# 数据库热路径第一阶段优化

状态：已实现并通过自动验收

日期：2026-08-23

## 背景

本项目曾在约 1000 份玩家存档、约 600 名在线玩家的部署规模下出现严重卡顿。全服务端混合负载已经证明当前业务行为、事务回滚和组合运行能够稳定完成，但进一步审查发现，部分高频查询仍因索引顺序不匹配而扫描全服数据，部分批量操作仍把一个逻辑动作拆成与购买量或条目数线性增长的 SQL。

本阶段只处理证据明确、职责边界稳定的数据库热路径。任务引擎、奖励公共层和觉醒请求级上下文不在本阶段重构，避免把低风险性能修复扩大成第二轮模块改造。

## 实施前与最终架构

```text
实施前
  HTTP 请求
    -> 按 player_id 读取角色、装备、物品、玛纳节点
       -> 主键不是以 player_id 开头
       -> SQLite 扫描全服表后过滤
    -> 批量购买、强化、装备操作
       -> 逐条读取或逐次累计
       -> SQL 数量随购买量 P 或条目数 N 线性放大

最终
  HTTP 请求
    -> player_id 前导索引
       -> 直接定位单个玩家的数据范围
    -> 请求级批量快照
       -> 一次读取参与本次操作的条目
       -> 在内存完成校验和最终状态计算
       -> 使用一次计数增量或有界批量写入
    -> 保持原有 SQLite 总事务和客户端响应结构
```

## 第一批玩家维度索引

第一批索引只覆盖已由生产查询和 `EXPLAIN QUERY PLAN` 证明存在全表扫描的高价值表：

| 表 | 索引前缀 | 主要调用 |
|---|---|---|
| `players_items` | `(player_id, id)` | `/load`、奖励和养成材料 |
| `players_characters` | `(player_id, id)` | `/load`、任务事实和角色养成 |
| `players_characters_bond_tokens` | `(player_id, character_id, mana_board_index)` | 角色序列化和觉醒资格 |
| `players_characters_mana_nodes` | `(player_id, character_id, value)` | `/load`、玛纳板和觉醒 |
| `players_equipment` | `(player_id, id)` | `/load`、装备批量操作和奖励 |
| `players_category_missions` | `(player_id, category, id)` | 普通任务和角色觉醒任务 |
| `players_mails` | `(player_id, id DESC)` 与 `(player_id, receive_time, id DESC)` | 邮件分页、未领取列表和计数 |
| `players_receive_history` | `(player_id, create_time DESC, id DESC)` | 领取记录分页与时间过滤 |

不在本阶段为全部玩家表批量创建索引。后续索引必须由实际查询计划、表规模和基准变化证明，避免无边界增加写放大和数据库体积。

## 商店计数

追忆装备强化当前按 `purchaseAmount` 循环调用购买计数接口。底层接口本身支持正整数增量，因此改为一次传入完整购买量。日、月、总累计和旧记录迁移逻辑保持不变。

`bulk_buy` 在进入事务时用两条 SQL 读取本批全部商品的日、月、总计数和两种旧记录，在内存完成库存校验。结算后每件商品用三条 UPSERT 写入最终计数，不再为每件商品重复读取；只有实际存在旧记录时才执行对应清理。两种旧记录同时存在时先取最大值，再与带商店类型的累计合并，并通过不可伪造的内部快照契约保证只迁移一次。

单件购买使用同样的计数快照语义。合并查询由现有复合主键定位到 `(player_id, shop_type, shop_item_id)`，避免为了减少 SQL 条数而退化成扫描该玩家全部历史计数。数据库计数、合并值和写入后的最终值均须为非负安全整数；破损值或溢出会在删除和写入前拒绝。

## 装备批量操作

装备批量觉醒和批量分解使用现有 `getPlayerEquipmentsByIdsSync()` 一次读取请求涉及的唯一装备。保护状态、持有状态、重复 ID、堆叠数量和奖励均从同一请求快照计算；事务内只执行计划好的更新。

客户端当前要求返回完整装备列表，因此提交后的一次完整装备读取暂时保留。本阶段只消除校验与执行阶段对同一装备的重复读取，不改变响应字段或把完整响应缩成增量响应。

## 玛纳板批量写入

玛纳学习继续在进入事务前完成内容、材料和节点规划。事务内：

1. 使用请求开始时已有的物品快照写入最终材料数量，不再为每种材料重新读取库存；
2. 同一角色本次新增节点使用一条多值 INSERT；
3. 同一角色本次觉醒节点使用一条受 player、character 和 node 集合约束的批量 UPDATE，并校验实际更新数量；
4. 玩家货币、任务事实、羁绊和进化等级继续处于原有总事务中。

本阶段不改变觉醒解锁对账。它仍可能重建全量任务上下文，留待下一阶段通过候选角色和请求级事实快照单独优化。

## 行为与错误边界

- 不改变 HTTP 路由、请求字段、MsgPack 响应字段或客户端错误语义；
- 不改变商店库存周期、旧购买记录迁移、装备保护、分解奖励和能力魂规则；
- 不改变玛纳节点父子关系、材料成本、进化等级或觉醒解锁条件；
- 任一批量条目失败时继续回滚整个原有事务；
- 索引通过幂等 `CREATE INDEX IF NOT EXISTS` 随现有数据库初始化执行，不要求服主手工迁移；
- 不增加缓存常驻玩家存档，不引入异步写队列或外部数据库。

## 后续存档读取与长写入整理

普通任务存档列表原先先读取类别，再按每个类别分别读取任务与阶段，查询次数会随玩家拥有的任务类别增长。当前改为一次读取该玩家全部类别任务、一次读取全部阶段，并在内存按类别和任务分组；返回结构保持不变，固定为 2 次查询。

账户、角色、邮件、任务事实、队伍、关卡状态和活动履历等高参数写入使用显式列名，并优先采用命名绑定或独立参数构造器。该整理用于让字段与参数一一对应，降低 schema 演进时发生位置错位的风险；已有批量写入和事务边界保持不变，不把一条批量 SQL 拆成逐记录数据库往返。

## 自动验收

实现采用测试先行：

1. 查询计划测试先证明目标查询仍为 `SCAN`，再要求改为目标索引 `SEARCH`；
2. 装备强化测试锁定一次购买只调用一次完整计数增量；
3. 批量商店测试锁定一次批量计数快照、库存与旧记录迁移语义；
4. 装备测试锁定批量读取次数、保护状态、重复 ID、回滚和最终完整列表；
5. 玛纳测试锁定材料免重读、节点批量写入、更新数量不符时回滚；
6. 运行商店、邮件、装备、玛纳专项回归和非多人混合负载；
7. 对比 `load/shop/mail` SQL 上界及行为签名，最后执行完整验证门禁。

## 实施结果

- 九个目标查询的真实 `EXPLAIN QUERY PLAN` 均从裸表扫描变为指定玩家前导索引的 `SEARCH`；初始化保持幂等，既有数据库会在正常启动初始化时获得索引。
- 追忆装备强化的购买量只提交一次完整增量。无旧记录的单件购买计数从验收中间态的 `7 SELECT / 3 UPSERT / 2 DELETE` 收敛为 `2 / 3 / 0`；两件批量购买为固定 `2 SELECT / 6 UPSERT / 0 DELETE`，读取次数不随商品数增长。
- `bulk_upgrade`、`sell_stack` 和 `bulk_sell_stack` 对请求内唯一装备只执行一次有界 `IN` 读取，事务内不逐件重读；客户端所需的提交后完整装备列表仍保留一次读取。唯一装备 ID 上限为 32765，超限在 SQL 前拒绝。
- 玛纳学习复用一次物品快照，同一角色新增节点使用一条多值 INSERT；觉醒节点使用一条 CTE UPDATE。觉醒 helper 自带事务或嵌套 savepoint，实际更新数不符时不会留下部分更新。单批唯一节点上限为 10922，`awake_level = 0` 继续表示“已学习但未觉醒”。
- 所有批量失败路径继续回滚货币、物品、节点、装备、进化、任务事实和奖励，不改变客户端响应与错误语义。

## 轻量混合基准

最终状态下连续两轮独立轻量基准结果一致。该 profile 只有 7 份独立存档、7 个活跃身份和并发 2，用于行为与 SQL 回归，不代表约 1000 存档、600 活跃身份的正式容量：

| 场景 | 读取上界 | 写入上界 |
|---|---:|---:|
| auth | 8 | 3 |
| load | 50 | 6 |
| mission-progress | 14 | 1 |
| single-battle | 116 | 29 |
| shop | 39 | 5 |
| gacha | 82 | 8 |
| mail | 31 | 4 |

与本阶段前的稳定轻量结果相比，`load` 保持 `50/6`，`mail` 保持 `31/4`，`shop` 从 `44/5` 降至 `39/5`。七个场景均为零错误、行为签名稳定、回滚验证通过。轻量报告的 `loadProfileValid=false` 和 `admitted=false` 仅表示未使用 formal profile。
