# 土俑累计分奖励

> 客户端验收：已通过（2026-07-19）。累计分奖励到账、动画提示和防重复领取均符合预期。

## 官方流程

土俑累计分奖励在 `single_battle_quest/finish` 中自动结算，不存在手动领取端点：

1. 服务端计算本次关卡分数，并更新该 folder 的最佳分。
2. 累计最佳分等于各 folder 最佳分之和。
3. 服务端查找所有“分数已达标且尚未发放”的奖励档位。
4. 奖励发放成功后记录奖励行 ID，并在 `carnival_event.reward_ids` 中返回本次行 ID。
5. 客户端仅在 `is_record_valid=true` 且 `reward_ids` 非空时保存奖励提示状态。
6. 返回土俑页面后，客户端根据挑战前后累计分和本地主数据播放奖励动画。

`reward_ids` 保存的是累计分奖励主数据行 ID，不是道具 ID。

奖励动画还会用 `leader_character_id` 创建像素角色。真实结算请求通常不含独立的 `party.leader` 字段，因此服务端必须回退到 `party.characters[0]`；返回 0 会使客户端尝试加载角色键 0，并报 `C8601`。

## 持久化

- `players_carnival_event_records`：各 folder 的最佳分和上次挑战队伍。
- `players_carnival_event_rewards`：已发放奖励，主键为 `(player_id, event_id, reward_id)`。
- `players_degrees`：持有称号，主键为 `(player_id, degree_id)`。

分数更新、奖励发放和奖励行登记处于同一 SQLite 事务中。任一步失败都会回滚，避免出现“记录已领取但奖励未到账”或重复发放。

完整存档导出、恢复和面板克隆同时包含：各 folder 分数记录、累计分奖励领取记录和持有称号。旧版存档没有这些可选字段时按空数据兼容；新版存档恢复后不会因为丢失领取记录而重复发奖。存档替换由一个总事务包裹，任一模块恢复失败时保留原存档。

当前事务边界只覆盖 Carnival 子流程。通用关卡结算（体力、经验、普通掉落、任务统计等）发生在此前，尚未与 Carnival 子流程合并为一个总事务；若 Carnival 发奖阶段异常，Carnival 的分数和奖励会回滚，但此前通用结算可能已经写入。全面原子化需要后续统一单人/多人结算事务。

## 旧存档兼容

旧服务端已经保存分数，但从未发放累计分奖励。修复后不以“是否刚跨过阈值”推测领取状态，而是以领取表为准：

- 总分已达标、领取表无记录：下一次成功挑战时补发。
- 领取表已有记录：不重复发放。
- 本次分数没有提高：仍可补发旧服务端遗漏的档位。

客户端不会用 `reward_ids` 决定弹窗中的奖励行，而是比较 `previous_total_best_score` 与刷新后的当前总分。补发旧档位时，服务端会把本次响应中的“弹窗用旧分数”下调到最低待补档位之前；这只影响动画区间，不修改数据库中的真实最佳分。

玩家 17 的活动 `250604` 当前累计最佳分为 `5,729,232`，领取表为空时应补发 29 档；补发成功后再次挑战应返回空 `reward_ids`。

## 验证重点

- 未达新档位时不弹窗、不发奖。
- 一次达到多个档位时全部发放，`reward_ids` 为对应行 ID。
- 道具、装备、星导石、玛纳、经验池和称号均正确到账。
- 同一装备多次获得时只在响应中返回最终堆叠状态。
- 称号出现在 `/profile/get_degree_list` 中，但不会自动替换当前展示称号。
- 事务失败时分数、奖励和领取记录全部回滚。
- 导出并恢复完整存档后，分数、领取记录和持有称号保持一致。
- 请求不含 `party.leader` 时，奖励动画使用首位主角色，不能返回 `leader_character_id=0`。
