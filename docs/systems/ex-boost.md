# EX 能力抽取状态

CN 客户端把 EX 能力流程拆为三个请求：`first_draw` 直接写入首次结果；普通 `draw` 只返回候选；随后
`select` 只发送 `is_confirm`，不会把 `character_id`、状态或能力列表回传。因此普通抽取后的候选结果属于服务端
必须持久化的玩家状态，不能只放在进程内存。

## 持久状态

schema 14 新增 `players_ex_boost_pending_draws`，每个玩家最多一条，保存角色、状态 ID 和能力 ID 列表。该表：

- 通过角色复合外键保证候选只能指向玩家已持有角色；
- 登记在存档 V2 的 `core` 领域，导出、恢复、克隆均覆盖；
- schema 13 存档缺少该表时按空候选兼容，schema 14 存档缺表则拒绝恢复；
- Server Bundle 目标数据版本同步为 14。

## 事务边界

- `first_draw`：扣材料与写角色 EX 能力同成同败；
- `draw`：扣材料与 UPSERT 待选结果同成同败；
- `select(false)`：删除候选，不修改角色；
- `select(true)`：写角色 EX 能力与删除候选同成同败，写入失败后仍可重试。

空能力列表序列化为数据库空字符串时会明确反序列化为 `[]`，不再产生无效能力 ID `0`。

`tools/ex_boost_pending_draw.test.cjs` 在抽取后清除路由模块缓存并重新注册路由，模拟服务重启；随后确认候选仍可
选择并写入角色。概率表和动画表现不由本事务测试代替，仍需客户端验收。
