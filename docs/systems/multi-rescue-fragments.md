# 多人救援碎片兼容奖励

## 目标与边界

银币碎片、金币碎片和紫币碎片是多人救援结算资源。当前服务端尚未完整恢复官服救援通知和参与身份链路，而单人部署主要依赖 NPC 或普通多人房间，因此管理后台提供两个本节点策略开关。

第一开关表示“将本服所有多人房间视为合法救援房间”，只影响本服所属真人玩家，不改变其他服务器，也不发布铃铛。第二开关表示“允许本服房主自救”，当前还要求第一开关开启。两者默认开启，持久化在各节点自己的 `server_gameplay_settings`。

## 发放规则

一次多人 finish 同时满足以下条件时发放：

- 本地 `/start` 成功时冻结的 `rescue_fragment_eligible` 为 true；Host 还要求当时的总开关和房主自救开关都开启，Guest 只要求总开关开启；
- 本次关卡成功完成；
- 当前多人关卡存在银、金或紫币碎片映射。

资格只在本地 `/start` 成功创建 active quest 时冻结到 `players_active_quests.rescue_fragment_eligible`；`/finish` 读取事务内重新取得的 stored active quest，不再按当时后台设置或请求身份重算。重赛会重新读取当时设置。旧 active quest 升级到 schema 22 后为 false，单人 active quest 强制 false。NPC 没有本地玩家 `/start`、active quest 或 `/finish`，因此不会发放。失败、中止、单人结算和未映射关卡也不发放。发奖位于现有多人 finish 总事务内，并受 active quest 幂等边界保护，结算回滚时碎片写入一并回滚。

支持范围包含永久领主、活动协力领主、世界故事活动领主、战阵协力和活动机兵等具有多人救援语义的关卡。碎片档位优先依据当前 CN 内容表中的关卡分组、难度和救援点数配置生成，不对未知分类或纯数字后缀作泛化猜测。

CN 客户端在多人 Advent 结算中可能提交 `ADVENT_EVENT_SINGLE`（category 7）。服务端在生成和查询救援碎片 reward key 时将其归一化为 `ADVENT_EVENT_MULTI`（category 8），因此两类 category 共用同一官方多人 Advent 关卡表。这只是结算输入归一化，不引入铃铛 attention、关注关系、救援游客资格或严格救援来源判断。

## 客户端显示

服务端使用统一奖励写入层增加玩家物品库存，并把本次碎片放入 `item_list`。真实物品 ID、`players_items` 和 `item_list` 是权威展示来源。

`drop_additional_reward_ids` 只发布当前 CDN `additional_reward_rules.json` 产生的官方组。此前为碎片临时投影的 `490000`、`490001`、`490002` 不是官方组，官方 CN 客户端解析时会因查不到 group 触发 C8601；这些伪展示组已移除。

这是明确的兼容模式：不实现铃铛 attention、`attention_key` 或随机招募。A、B 两个节点的设置互不影响。后续如需严格官服来源判定，应独立设计并验收。

## 证据等级

客户端与 CN 内容表能够支持碎片物品、多人关卡范围和难度档位；“每次固定 10 个”参考了已有玩家验证的部署实现。将所有多人房间统一视作救援来源，并允许房主自救，是为当前单人服使用方式增加的明确服主策略，不是官服行为复原。

后续实现严格救援来源后，应新增独立的来源判定和客户端联机验收，再由服主决定是否关闭本兼容开关；不应在本模块内混入房间发现、救援通知或跨服身份职责。
