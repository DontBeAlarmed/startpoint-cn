# 深渊连战专属武器、模式门控与兑换商店设计

日期：2026-07-13

状态：已获用户批准，待实施

适用项目：StarPoint CN / World Flipper CN 1.4.x 模组工具链

## 1. 目标

为现有自制连战内容补齐一条可测试、可发布、可回滚的奖励闭环：

1. 保留已经分配的 15 个装备 ID `8000101`–`8000115`，制作六属性各两把、通用三把的原创武器素材。
2. 将现有克隆占位词条替换为极强的测试词条，使“生效/未生效”的差异能在伤害、HP 或技能槽上立即观察。
3. 让这些词条只在深渊连战、自制宝物域连战和木桩假人中生效；其他任务中装备仍可显示，但不装载任何战斗效果。
4. 使用深渊代币 `2370099` 建立 `700099` 独立活动兑换商店，售卖全部 15 把武器。
5. 将客户端主数据、服务端镜像、图片、发布工具、客户端补丁和验证说明组成可重复执行的完整链路。

本版本是“功能验证版”，数值不作为最终平衡方案。

## 2. 已确认的现状

- 深渊连战活动 ID 为 `700099`，任务 ID 为 `700099001` 起的多轮 Rush Event。
- 自制宝物域 Boss 连战使用 Challenge Dungeon Event 任务 `2001`；原版 `2002`–`2006` 未挂载自制多层 floor。
- 木桩假人位于 `master/quest/practice/practice_quest.orderedmap`，对应 `Practice` 任务 ID `1`–`97`。`1001+` 是 Boss 练习或试炼，不属于本设计的木桩白名单。
- 深渊代币 `2370099` 和装备 `8000101`–`8000115` 已有占位骨架；装备名、说明、词条和图片仍借用官方供体。
- `rush_event[700099]` 当前仍引用旧代币 `2370007`，必须改为 `2370099`，并同步修正生成脚本，避免重跑回退。
- 当前 `event_item_shop` 中 ID `700099` 只是借用 `700004` 的过期单条商品，不是深渊专属商店。
- 客户端的 `AbilitySoulAbilityLogic` 同时承载武器能力和能力魂，原生 `questKind` 为 `Option.None`；仅改主数据无法实现真实的模式限定。

## 3. 方案选择

### 3.1 采用方案：客户端能力装载门控 + 原生活动道具商店

在 `BattleCharacterLogic.getAvailableAbilities` 中识别 `AbilitySoulAbilityLogic.id` 是否位于 `8000101`–`8000115`。命中时覆盖原始可用性判断，只允许三类任务；未命中时保持官方逻辑不变。

商店继续使用客户端已有的 `ShopType.EVENT_ITEM` 和 Rush Event 兑换入口。这样可以复用官方商品列表、购买、库存和货币扣除界面，无需新增顶层 UI。

### 3.2 未采用方案

- **仅写描述、数据不门控**：普通关卡仍会加载词条，不能满足“模式专属”。
- **服务端在 battle/start 拒绝编队**：词条在客户端仍会显示并参与本地构建，体验与实际规则不一致，也无法可靠覆盖木桩。
- **新建完整顶层商店 UI**：需要大量客户端场景、导航与素材补丁，风险明显高于复用原生活动兑换页。

## 4. 生效范围

客户端门控只放行：

| 类型 | 客户端枚举 | ID 条件 |
|---|---|---|
| 深渊连战 | `SingleQuestIdKind.RushEvent`，index `17` | `floor(questId / 1000) == 700099` |
| 自制宝物域连战 | `SingleQuestIdKind.ChallengeDungeonEvent`，index `8` | `questId == 2001` |
| 木桩假人 | `SingleQuestIdKind.Practice`，index `10` | `1 <= questId <= 97` |

明确排除：

- Challenge Dungeon `2002`–`2006`
- Practice `1001+`
- 技能预览、教学、普通剧情、多人战及其他活动

门控覆盖武器本体与由相同 `ability_soul` ID 生成的能力魂，防止通过魂珠绕过限制。

## 6. 图片素材

为 15 把武器生成 15 张独立原创 `1024x1024` RGBA PNG：

- 透明背景、无文字、无角色、单件武器居中。
- 轮廓在装备列表缩略图下仍能快速辨认。
- 火、水、雷、风、光、暗分别使用红橙、蓝青、黄紫、绿青、白金、黑紫配色与原创元素纹章。
- 两把同属性武器必须有不同武器类型和主轮廓。
- 三把通用武器使用黑银、深紫和虹彩深渊材质，不绑定单一元素色。
- 不复刻官方武器、商标或角色标志。

源 PNG 固定保存在 `mod-tools/assets/abyss-equipment/`。装备与客户端 `pixelart` 逻辑路径使用以下固定映射：

```text

8000102 -> item/equipment/mod/abyss/fire_02
8000103 -> item/equipment/mod/abyss/water_01
8000104 -> item/equipment/mod/abyss/water_02
8000105 -> item/equipment/mod/abyss/thunder_01

8000107 -> item/equipment/mod/abyss/wind_01
```

发布时仅执行标准 PNG 到游戏存储态 PNG 的魔数转换，不做有损重编码；用项目现有 SHA-1 逻辑路径规则写入 upload/diff。

## 7. 深渊兑换商店

### 7.1 商店身份

- Shop 类型：`EVENT_ITEM` (`4`)
- Event 类型：Rush Event (`11`)
- Event ID：`700099`
- 货币：`2370099` 深渊代币
- 商品 ID：`9700101`–`9700115`
- 有效期：与深渊活动一致，测试版保持 `2000-01-01` 至 `2099-12-31`

商品 ID 使用独立高位区间，避免服务端当前按 `shop_item_id` 全局记录购买次数时与已有商店发生冲突。

### 7.2 价格与库存

| 商品 | 单价 | 库存 |
|---|---:|---:|
| 12 把属性武器 | 10 深渊代币 | 每把 5 |
| 3 把通用武器 | 15 深渊代币 | 每把 5 |

总毕业成本为 `825` 代币。当前每轮掉落 5 枚、15 轮完整通关获得 75 枚，约 11 次完整通关可兑换全部库存。

商品显示顺序严格按装备 ID 升序排列。每条商品的奖励类型为 `ShopItemRewardType.EQUIPMENT` (`4`)，奖励 ID 为对应装备 ID，数量为 1。

### 7.3 同步数据

客户端：

- `master/shop/event_item_shop.orderedmap`
- `master/quest/event/rush_event.orderedmap` 的 `700099` 代币字段

服务端：

- `assets/event_item_shop.json`
- `assets/event_item_shop_id_map.json`
- 现有装备、元素、最大等级、lookup 与 item ID 镜像

`assets/event_item_shop.json` 固定写到 `11 -> 700099 -> 9700101..9700115`；ID map 的每条记录固定为 `{ "eventType": 11, "eventId": 700099 }`。生成工具必须从客户端表、服务端商品 JSON 和 ID map 删除当前过期的占位商品 `700099`，并保证重复执行结果幂等。

## 8. 工具与文件边界

扩展现有 `mod-tools/wf_rogue_rewards.py`，让它成为装备、能力魂、服务端镜像和活动代币的确定性生成入口。新增 `mod-tools/wf_rogue_shop.py` 专门生成 51 列客户端商品行及两个服务端商店 JSON，避免把商店表结构混入战斗奖励脚本。

客户端门控固定交付到 `client-patch/abyss-mode-equipment/`，素材固定交付到 `mod-tools/assets/abyss-equipment/`。补丁模块包含：

- 可重复执行的补丁脚本
- 补丁前签名检查
- 已补丁检测
- 失败时不写输出的 fail-closed 行为
- README 中的应用、验证与回滚步骤

战斗运行时只修改已有调用点 `BattleCharacterLogic.getAvailableAbilities`；反编译静态搜索确认 `getAvailableAbilitiesWithCond` 没有外部调用点，本版本不扩大补丁面。

由于测试词条极强，发布必须 fail-closed：装备/能力魂生成器可以独立 dry-run 和写入本地备份，但 `--publish` 只有在客户端补丁验证命令确认目标产物已含门控后才允许继续。禁止先发布超模词条、后安装客户端补丁。

不直接修改或提交 `web/pages/`、`src/routes/web/`、`web/public/`，也不纳入其他本地逆向目录或无关工作树改动。

## 9. 错误处理与回滚

- 所有 orderedmap 写入先 dry-run，再由现有备份机制生成 `.bak-wfmod-*`。
- 生成器只允许覆盖保留区间 `8000101`–`8000115`、`9700101`–`9700115` 和明确的旧占位商品 `700099`；发现这些键被其他内容占用时先终止并报告差异。
- 写入后立即复读并校验 15 个装备键、15 个 ability_soul 键、15 个商店键和代币字段。
- 图片发布前校验 PNG 签名、尺寸、透明通道和逻辑路径哈希。
- 客户端补丁只有在目标方法签名与预期一致时才应用；匹配数量不为 1 时终止。
- 服务端 JSON 更新使用稳定排序和幂等覆盖，避免重复商品。
- 回滚时恢复 orderedmap 备份、删除新增 hashed asset，并恢复服务端 JSON 的变更前版本。

## 10. 验证标准

### 10.1 静态与自动验证

1. 词条描述器输出与第 5 节目标一致。
2. `8000101`–`8000115` 的装备、元素、能力魂、图片路径和服务端 lookup 一致。
3. `9700101`–`9700115` 在客户端表、服务端商店和 ID map 中一一对应。
4. `rush_event[700099]` 显示货币 `2370099`。
5. 补丁静态检查只影响 `AbilitySoulAbilityLogic.id` 的指定区间。
6. 运行服务端 `npm run typecheck`，并执行相关 Python dry-run/readback 检查。

### 10.2 客户端/真机验证

至少验证以下矩阵：

| 场景 | 预期 |
|---|---|
| Rush `700099` | 词条生效 |
| Challenge Dungeon `2001` | 词条生效 |
| Practice `1`–`97` 中至少两个不同属性木桩 | 词条生效 |
| Challenge Dungeon `2002` | 词条不生效 |
| Practice `1001` | 词条不生效 |
| 任一普通剧情关 | 词条不生效 |

商店验证包括列表加载、代币显示、余额不足、单次购买、库存递减、重复进入库存保持、装备到账和满库存拦截。

最终发布后同步到当前 MuMu 客户端并重启游戏，以真机截图或战斗数值记录确认生效范围。

## 11. 非目标

- 本版本不追求最终数值平衡。
- 不为商店新增顶层入口或全新场景。
- 不修改原版宝物域 `2002`–`2006`。
- 不让 Boss 练习、技能预览或教学关获得专属词条。
- 不在本任务中切换或删除旧后台管理界面。
