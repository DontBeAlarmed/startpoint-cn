# 邮件附件搜索与定向发送设计

> 日期：2026-07-19
> 状态：仅完成分析，尚未实现
> 范围：管理后台邮件附件搜索、指定存档/账号/全服发送
> 不包含：修改游戏客户端、实时邮件推送、管理后台公网鉴权

## 结论

这两项需求不需要修改游戏客户端，也不需要重写游戏内邮件协议：

1. 附件搜索应在 React 管理后台 `/admin/mail` 中复用现有 lookup API，按附件类型加载中文名称并在前端过滤；点击候选只填写附件 ID，最终合法性继续由 `/api/mail/send` 校验。
2. 服务端已经支持 `playerId`、`accountId` 和全服三种目标。当前主要缺口是旧 `/mail` 页面只能全服发送，以及 `/admin/mail` 使用默认只返回 25 条记录的玩家列表，导致指定存档下拉不完整。
3. 正式补全时应同时解决批量发送的原子性和重复提交问题，避免“部分发送成功但仍返回成功”或双击产生重复邮件。

## 当前实现

### 两套管理页面

- 旧页面 `/mail` 是静态 Tailwind 表单，只提交附件信息，不提交目标，因此固定走全服发送。
- 新页面 `/admin/mail` 使用 React、Ant Design 和 React Query，已经提供“全服、指定账号、指定存档”三档选择和发送确认弹窗。
- 两套页面共用 `POST /api/mail/send`。JSON 请求返回 JSON，旧表单请求继续使用重定向结果。

后续功能应优先落在 `/admin/mail`。旧页面在管理后台迁移完成前保持兼容，最终可重定向到新页面，避免长期维护两套交互。

### 当前发送目标语义

后端现有优先级为：

```text
playerId > accountId > 未提供目标时全服
```

- `playerId`：只向指定 `players.id` 存档插入一封邮件。
- `accountId`：向该账号下的所有存档发送，不只是当前默认存档。
- 全服：展开所有账号的所有存档，因此是“每个存档一封”，不是“每个账号一封”。

设备绑定和全局活动存档不应参与邮件目标解析。游戏内邮件列表、领取和 `mail_arrived` 都按当前存档的 `player_id` 工作；其他存档切换并重新加载后即可看到各自邮件。

### 当前缺陷

1. `/admin/mail` 通过无参数 `GET /api/player` 加载存档，而该接口默认分页大小为 25，超过 25 个存档后下拉列表不完整。
2. 存档候选只显示昵称和存档 ID，没有账号归属，重名时容易选错。
3. JSON 请求若漏传目标会静默退化为全服发送，风险过高。
4. 同时传入 `playerId` 和 `accountId` 时会静默优先使用 `playerId`，请求语义不明确。
5. 逐存档插入时会吞掉异常，可能出现部分发送成功，甚至全部失败仍返回 `ok: true`。
6. 没有持久化幂等键，重复点击或网络重试可能重复发信。
7. 整数使用 `parseInt`，会接受 `12x` 等部分非法字符串。
8. 旧 `/mail` 路由把查询参数直接插入 HTML，存在反射型 XSS 风险。

## 附件名称与 ID 搜索

### 可复用数据

现有 `GET /api/lookup/*` 已覆盖全部需要 ID 的附件类型：

| 附件类型 | Lookup API | 名称来源 | 当前数量 |
|---|---|---|---:|
| 道具 `type=1` | `/api/lookup/items` | `assets/item_lookup.json` | 1284 |
| 角色 `type=5` | `/api/lookup/characters` | CN 角色与角色文本数据生成表 | 505 |
| 装备 `type=6` | `/api/lookup/equipment` | `assets/equipment_lookup.json` | 436 |

三套名称表与后端邮件合法 ID 集合当前完全对应，无缺名或多余 ID。道具和角色存在大量重名；同一个数字 ID 还可能在不同附件类型中表示不同对象，例如装备本体和对应魂珠。因此必须先选择附件类型，再在该类型内搜索，不能把三类数据混成一个候选池。

### 推荐交互

1. 保留附件类型选择框。
2. 仅在道具、角色、装备类型下显示可搜索的 Ant Design `Select`。
3. 按当前类型懒加载一份 lookup，并用 React Query 永久缓存本次页面会话的数据。
4. 中文查询做 Unicode `NFKC` 标准化后进行子串匹配。
5. 纯数字查询只接受完整 ID 精确匹配，避免输入 `50` 返回 `5010028`。
6. 结果按“名称前缀命中、名称包含命中、ID 升序”排列，最多渲染 20 条。
7. 每项始终显示名称和 ID；角色补称号、星级、属性，装备补星级和分类，用于区分重名。
8. 点击或按 Enter 选择候选后填写 `type_id`；角色和装备同时把数量固定为 1。
9. 切换附件类型时清空搜索词和旧 `type_id`，防止道具 ID 残留到装备或无 ID 的资源奖励。
10. 候选只负责填表，不能直接发送；现有确认弹窗必须保留并显示最终类型、名称、ID 和数量。

三份 lookup 总计规模较小，前端本地过滤足够，不需要新增服务端搜索接口。最终提交仍必须经过 `/api/mail/send` 的权威校验，不能只依赖候选是否命中。

## 定向发送设计

### 目标列表

新增专用只读接口：

```text
GET /api/mail/targets
```

建议响应：

```json
{
  "accounts": [
    {
      "accountId": 12,
      "players": [
        { "playerId": 101, "name": "冒险者", "isDefault": true }
      ]
    }
  ],
  "accountCount": 1,
  "playerCount": 1
}
```

该接口必须返回完整列表，不复用默认 25 条的玩家分页。存档候选显示为“昵称 · 存档 #101 · 账号 #12”，账号候选显示为“账号 #12 · 3 个存档”。只返回内部账号 ID、存档 ID、昵称和默认标记，不返回设备、登录、viewer 或 session 信息。

### 显式请求模型

新管理后台使用显式目标，避免字段缺失时意外全服发送：

```json
{
  "requestId": "UUID",
  "target": { "mode": "player", "playerId": 101 },
  "type": 4,
  "typeId": null,
  "number": 100,
  "subject": "补偿",
  "description": "邮件正文"
}
```

另外两种目标为：

```json
{ "mode": "account", "accountId": 12 }
{ "mode": "all" }
```

JSON 请求必须显式提供且只能提供一种目标。旧 HTML 表单可以在迁移期继续兼容“未提供目标即全服”，但必须显示明确的全服确认步骤。

### 验证、事务与幂等

- 所有整数严格解析，拒绝小数、指数形式、尾随字符和 int32 越界。
- 存档或账号不存在时拒绝；账号存在但没有存档时返回冲突，不能成功发送 0 条。
- 只有道具、角色、装备可以携带 `typeId`；其他附件类型携带多余 ID 时拒绝。
- 保留现有 CDN ID 校验、数量上限、角色/装备数量必须为 1、标题 64 字、正文 512 字的规则。
- 在一个 SQLite `IMMEDIATE` 事务中重新解析收件人并插入整批邮件；任一插入失败则整批回滚，不再静默跳过。
- 增加持久化发送记录，以 `request_id UNIQUE` 实现幂等。
- 相同 `requestId` 和相同内容重试时返回原结果，不再插入；相同 ID 携带不同内容时返回冲突。
- 每个收件存档仍生成独立的 `mail_id`；批次使用单独的 `sendId`，不能共享一条游戏邮件 ID。

## 实施范围

建议按两个可独立审查的模块实施和提交：

### 模块一：附件搜索

- `admin/src/pages/Mail.tsx`：按类型加载 lookup、候选过滤、搜索选择、切换类型清空状态、确认框展示名称。
- 不新增搜索后端；复用现有 `src/routes/web_api/lookup.ts`。

### 模块二：安全定向发送

- `src/routes/web_api/mail.ts`：显式目标 DTO、严格验证、目标列表接口、幂等响应。
- `src/data/domains/mail.ts`：完整收件人查询与批量事务插入。
- `src/data/initializers/wdfpData.ts`：持久化管理邮件发送记录。
- `admin/src/pages/Mail.tsx`：使用专用目标接口并生成 `requestId`。
- `src/routes/web/mail.ts`：移除未经转义的查询参数插值。
- 旧页面补齐安全确认或重定向到 `/admin/mail`。

## 验收清单

### 附件搜索

- 中文全名和部分名称均可搜索，排序稳定且最多 20 条。
- 全角数字经标准化后可按完整 ID 命中；数字子串不会误匹配长 ID。
- 同一个 ID 在道具和装备类型下显示各自对象，类型互不污染。
- 重名候选可由附加信息区分。
- 点击、方向键和 Enter 都能正确选择；切换类型清空旧 ID。
- lookup 加载失败时阻止提交并显示错误。

### 定向发送

- 存档超过 25 个时仍能列出全部目标，并正确显示账号归属。
- 指定存档只写入该存档；账号模式只写入该账号全部存档；全服写入所有存档。
- 不存在目标、零存档账号、非法整数和歧义目标均被拒绝。
- 第 N 条插入失败时整批回滚，没有部分邮件和伪成功历史。
- 相同 `requestId` 重试只生成一批，不同内容复用同一 ID 时被拒绝。
- 指定存档能在游戏内看到并领取邮件，奖励只进入该存档，领取后 `mail_arrived` 正确恢复。
- 使用临时 SQLite 和 Fastify `inject` 自动测试，禁止向实际测试存档执行自动群发。
- 服务端通过 TypeScript 编译，管理后台通过生产构建，并人工检查桌面和手机宽度。

## 已知安全边界

当前管理 API 没有认证、授权和发送限流。服务仅在可信本机环境使用时风险可控；若配置为局域网或公网监听，必须先单独补齐管理鉴权。这不阻塞本轮邮件功能设计，但实施时不能把 lookup 或目标列表暴露给未授权访问者。
