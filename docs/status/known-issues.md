# 当前已知问题与限制

本文只保留尚未解决、明确受限或需要重新确认的问题。已经修复并通过客户端验收的历史问题由 Git 记录，不继续堆叠在这里。自动测试状态和客户端验收状态必须分别查看[支持矩阵](./support-matrix.md)与[测试进度](./test-progress.md)。

## 任务系统 P0

任务模块当前只能标记为“部分完成”，下一阶段必须先修正正确性基础，再扩展分类：

1. 单人战斗的部分角色觉醒 tracker 没有统一受成功结算约束，失败战斗仍可能累计通关、编队、种族、Power Flip 或 Dash 条件。
2. `update_mission_progress` 的主数据 pattern 列读取不统一。Regular、Collect-item、Degree 和 CharacterAwake 不能一律读取 `row[0]`。
3. 客户端上报 pattern 时缺少完整的开放期、category 和 event 范围限制，可能更新历史或未来的同名任务。
4. category 1、2、3、4、5、10 尚无完整通用自动结算链。普通任务没有独立的客户端手动领奖端点，需在业务响应中统一计算 `mission_info`、发奖和阶段状态。
5. Weekly 已注册到 Regular 计算器，但当前计算范围没有完整覆盖 category 10；游玩次数、通关次数和不同关卡数的语义仍需拆分。
6. Collect-item 缺少完整的库存或累计获得量模型，Degree 只覆盖少量等级任务，`/load` 的收集任务清单仍不完整。
7. 角色觉醒任务仍有已确认条件错误：配对计数写入与读取排序不一致；`2310012` 的种族组合错误；`3310032/3310033` 缺少指定关卡约束；空羁绊数组可能被误判为全部完成。

角色觉醒的“立即解锁第二页、手动回第一页领奖”核心时序已经通过客户端验收，但这不代表 144 条觉醒任务条件全部正确。详见[任务完成度审计](../systems/mission-completion-audit.md)与[角色觉醒任务](../systems/character-awake-missions.md)。

## Pass 任务缺失

客户端存在 PassDaily、PassWeek、PassEvent，即 category 6、7、8。当前缺少完整主数据转换、进度计算、阶段奖励和协议返回，只保留不足以形成完整玩法的基础响应。Pass 不能标记为已实现。

## 邮件通知未统一

`/load` 和邮件端点会按当前存档未领取邮件数动态计算 `mail_arrived`，但装备、抽卡、商店、任务、关卡和养成等大量普通业务响应仍硬编码 `false`。因此邮件到达后，客户端是否立即刷新取决于下一次经过的端点，通知语义尚未统一。

邮件附件领取已覆盖主要类型，但全部附件类型、领取与标记的总事务、异常回滚和通知刷新仍需专项测试。详见[邮件系统](../systems/mail.md)。

## 特殊关卡与联机

### 狂热激战常驻批次为推测性回退

官方 CN 1.4.54 主数据中，常驻批次 `700011` 至 `700017` 没有活动代币、文件夹代币奖励和商店商品。当前服务端把它们回退到 `700001` 至 `700007` 的配置，以提供可用商店和奖励流程；该映射有自动测试，但没有官方服务端抓包依据，必须保持“推测实现”标记，并等待客户端全流程验收。

### 战阵事件级奖励缺失

战阵的本地三队配队、开始和基础结算已经实现，事件级分数奖励仍没有完整主数据与结算链。战阵整体也尚未完成客户端重新验收，不能把服务端测试写成客户端通过。

### 超级猫头鹰多场景联机未实现

普通联机以一次 Boss 战后结算为主；超级猫头鹰 `BothBoss` 关卡需要在同一战斗会话内处理 `LevelNext`、下一场景 SceneReady 屏障和第二个 Boss。当前帧协议只具备基础 SceneReady，中间场景切换与恢复尚未补齐。详见[多场景联机分析](../protocol/super-owl-multiscene.md)。

### 自动连战体力耗尽

客户端自动连战模式可能在体力耗尽后继续请求 start；服务端当前按普通入场返回 H400，客户端无法优雅停止并可能退出流程。需要为 `is_auto_start_mode=true` 对齐官方非致命结束语义，不能直接免除体力校验。详见[体力系统](../systems/stamina.md)。

### 活动加成掉落缺失

部分奖励组预留了由活动 campaign 在运行时补入的掉落位置，当前未实现相应加成规则。活动开启时，实际掉落可能少于官方活动效果；在取得主数据与客户端依据前不应凭空补值。

## 账号、存档与入口功能

### 存档完整性

导入、导出和克隆已覆盖多个领域，但尚无针对所有玩家域、可选字段、事务回滚和跨版本恢复的完整端到端矩阵。新增领域表后若没有同步序列化与恢复逻辑，可能出现部分状态缺失。大规模导入前应保留数据库备份并用测试存档验证。

### 礼包码兑换

客户端入口可以被启用，但真实礼包码校验、兑换内容、次数限制和持久化尚未实现。现有兼容响应不等于礼包系统可用。

## 内容与客户端资源限制

### 首次标题资源与动画资源

- 首次没有完整 CDN 缓存时，标题画面可能找不到 `scene/title_bundled/logo/logo.movie.amf3.deflate`；完整下载后通常消失，仍需在全新安装流程复核。
- 官方 CN 1.4.54 资源集中缺少 `character_level_up_effect.frame.amf3.deflate`，当前通过资源完整性边界避免恢复循环，但对应动画资源并未补齐。

### 卡池与漫画图片

- CN 1.4.54 缺少部分早期或联动卡池的 `gacha_feature_content`，手动切换到相应运营时间时可能出现 C2032。服务端无法凭空生成官方图片。
- 漫画图片处理曾针对特定高分辨率设备调整；其他屏幕比例、纹理上限和完整翻页体验仍需设备矩阵复核。

### Mana Board 时间窗

部分角色的第二块玛纳板受 `mana_board2_open_condition` 时间窗控制。如果存档已经持有板二状态，但服务器时间早于开放时间，CN 客户端可能在切换板层时触发 F1009。当前运行时间应与存档进度保持一致；服务端尚未为所有角色实施按时间降级过滤。

## 待复核现象

以下现象缺少稳定复现或最新证据，暂不据此修改业务逻辑：

- 抽到新角色后，客户端可能把角色自动填入默认编队空位；需确认这是客户端原生行为还是服务端响应字段问题。
- 个别环境偶发 R1 连接失败，曾有“重建存档后恢复”的记录，但没有证明问题位于存档、网络还是旧客户端缓存。
- 角色剧情阅读后紫色未读标记是否能稳定清除，需要重新核对 `episode_trial` 的真实持久化协议。

复核结果应进入对应系统文档或测试矩阵，不在本文追加排查时间线。

## 已实现但仍待客户端验收

这些功能已有服务端实现和自动测试，但尚不能写成客户端通过：

- 狂热激战的配队、事务、商店与奖励回退；
- 无限演武的体力、评级、跨档奖励、动画响应和 load 持久化；
- 战阵的三队配队、start 与基础 finish；
- 歼灭者最高难度门票预扣、abort 返还和重启恢复；
- NPC 贡献昵称的客户端显示和重赛稳定性；
- 新管理后台的浏览器与多设备人工验收；
- 嵌入式契约与真实 Android、桌面宿主的集成。
